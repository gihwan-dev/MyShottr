# Inkbeam v0.2.0 Official Release Design

- Date: 2026-08-03
- Status: Normative design approved; editorial written-spec review pending
- Current product: `MyShottr v0.1.0`
- Target product: `Inkbeam v0.2.0`
- Current repository: `gihwan-dev/MyShottr`
- Target repository: `gihwan-dev/inkbeam`
- Distribution: free, direct download from GitHub Releases
- Update framework: Sparkle `2.9.4`
- Tagline: `Capture fast. Mark freely.`

## 1. Purpose and Authority

This document defines the complete one-time cutover from `MyShottr` to
`Inkbeam` and the first officially signed, notarized, updateable Inkbeam
release. It covers:

- the product and repository rename;
- the clean replacement of all MyShottr runtime identities;
- the `.inkbeam` editable project contract;
- the macOS app, embedded Native Messaging helper, and Chrome extension;
- Developer ID signing, Apple notarization, and stapled DMG packaging;
- Sparkle stable and beta update channels;
- staged `rc.1 -> rc.2 -> final` release validation;
- privacy, error handling, withdrawal, and release evidence.

This document fully supersedes
[`2026-08-02-inkbeam-rename-design.md`](./2026-08-02-inkbeam-rename-design.md).
The superseded document is historical design provenance only. Its requirements
for `.myshottr` compatibility, dual Native Messaging hosts, old/new app
coexistence, inbox migration, unsigned ZIP distribution, and no updater must
not be implemented.

The following earlier specifications remain authoritative only for product
behavior that this document does not replace:

- [`2026-07-29-myshottr-v1-design.md`](./2026-07-29-myshottr-v1-design.md)
- [`2026-07-30-myshottr-v1-public-release-design.md`](./2026-07-30-myshottr-v1-public-release-design.md)
- [`2026-07-31-myshottr-editor-ux-polish-design.md`](./2026-07-31-myshottr-editor-ux-polish-design.md)

If an older document conflicts with this document on identity, document
extension, migration, packaging, signing, notarization, updating, release
assets, or release acceptance, this document takes precedence.

## 2. Context and Confirmed Decisions

### 2.1 Current verified state

At the design baseline commit `b0d3622ba62e5d1822f13a29fae8b55ffd46b75a`:

- the working tree is clean;
- the app, helper, packages, and project format still use MyShottr identities;
- `v0.1.0` is deliberately unsigned and unnotarized;
- the release scripts expect ad-hoc signatures and Gatekeeper rejection;
- no automatic updater exists;
- Xcode and `notarytool 1.1.2` are installed;
- the local Keychain reports zero valid code-signing identities.

The user has enrolled in the Apple Developer Program, but official release work
cannot begin until a valid `Developer ID Application` identity is installed on
the release Mac.

### 2.2 Approved product and distribution decisions

- The product, macOS app, and public repository are named `Inkbeam`.
- The first Inkbeam release is `v0.2.0`.
- The app is initially free.
- Distribution is direct from GitHub Releases, outside the Mac App Store.
- Direct distribution is required to preserve the current Chrome Native
  Messaging installation architecture.
- The Mac App Store is deferred; it is not a second v0.2.0 channel.
- The primary macOS artifact is a signed, notarized, stapled DMG.
- The same final DMG is the Sparkle update archive.
- Sparkle 2 ships in v0.2.0.
- Developer ID, notarization, Sparkle signing, and GitHub publishing credentials
  stay on the local release Mac.
- GitHub Actions never receives release private keys.
- The release sequence is public `rc.1`, public `rc.2`, then final `v0.2.0`.
- First launch makes no automatic updater network request.
- Second launch asks once for automatic-check permission.
- Approved automatic checks run every 24 hours.
- Updates are never silently downloaded or installed.
- Sparkle system profiling, analytics, and telemetry are disabled.
- The current coral capture-frame icon and menu-bar icon remain for v0.2.0.
- Full-page capture, desktop mockups, and a visual-brand redesign are deferred.

### 2.3 Clean-cut decision

Inkbeam starts with one current identity and no MyShottr compatibility layer.
There is one known user and no requirement to preserve MyShottr documents,
preferences, history, Chrome host aliases, or pending capture data.

The implementation must therefore not include:

- `.myshottr` read, write, conversion, or in-place save support;
- the `com.myshottr.project` document type or UTI;
- `com.myshottr.*` bundle, helper, host, or notification aliases;
- scanning or importing `Application Support/MyShottr`;
- migration of MyShottr preferences, history, or recovery data;
- dual Native Messaging manifest registration;
- old/new app coexistence detection or a migration-blocked state;
- legacy capture inbox de-duplication;
- compatibility warnings or migration UI;
- automatic cleanup code for the old installation.

Existing MyShottr installation data is removed once from the developer machine
as a release-preflight operation. That cleanup is not shipped in Inkbeam.

## 3. Goals and Non-Goals

### 3.1 Goals

1. Expose one coherent Inkbeam identity across every live runtime and release
   surface.
2. Preserve the approved native region capture, Chrome visible-viewport
   capture, editor, save, export, and clipboard behavior.
3. Save and reopen editable projects using `.inkbeam` only.
4. Ship a universal macOS app and embedded helper signed with Developer ID,
   accepted by Apple notarization, and distributed in a stapled DMG.
5. Ship a fail-closed Sparkle update path with signed DMGs, signed feeds, and
   separate beta and stable channels.
6. Prove real installed-app updates from `rc.1` to `rc.2` and from `rc.2` to the
   final release.
7. Prevent updater behavior from bypassing modified-document save decisions.
8. Keep capture and document data local and send no optional system profile or
   analytics data.
9. Preserve `v0.1.0` as clearly deprecated historical evidence without keeping
   its runtime contracts alive.

### 3.2 Non-goals

- `.myshottr` compatibility or migration;
- Safari, Firefox, or other Chromium-browser support;
- full-page or scrolling capture;
- browser chrome capture;
- desktop, device, or presentation mockups;
- Chrome Web Store publication or extension auto-update;
- Mac App Store distribution;
- delta updates;
- background update download or silent installation;
- crash reporting, product analytics, telemetry, or account systems;
- custom Sparkle update windows;
- a user-selectable beta/stable channel switch;
- automatic downgrade;
- automatic replacement or deletion of the old MyShottr installation;
- rewriting Git history or historical `v0.1.0` release evidence;
- claiming that physical Intel hardware has been tested when it has not.

| Editor URL scheme | `inkbeam-editor` |
| WebKit bridge name | `inkbeam` |

| Acceptance Git note | `refs/notes/inkbeam-acceptance` |

Swift product types, test targets, source directories, environment variables,
temporary prefixes, editor entrypoints, app metadata, generated Xcode files,
release scripts, package names, and current documentation use Inkbeam naming.

Historical `v0.1.0` release notes, assets, tags, checksums, and Git history keep
their original MyShottr wording because they describe historical facts.

### 4.2 Editable project format

New captures save only as `.inkbeam` packages:

```text
Example.inkbeam/
├── manifest.json
├── original.png
└── document.json
```

The existing strict package validation, immutable original pixels, manifest
shape, and annotation schema remain unless a separate schema change is approved.
The rename changes the product contract and package extension, not annotation
meaning.

Inkbeam registers only `dev.gihwan.inkbeam.project`. It does not advertise,
open, convert, or save `.myshottr`. Attempting to open `.myshottr` produces the
standard unsupported-file result. It does not offer a migration path.

Inkbeam does not modify existing `.inkbeam` documents during an app update.
Any future schema migration requires its own versioned design.

### 4.3 Chrome extension identity

The Chrome extension keeps its current public manifest key and therefore its
deterministic extension ID. The key is public identity material, not a private
credential or a MyShottr compatibility path.

The extension permissions remain exactly:

```json
["activeTab", "nativeMessaging"]
```

The extension adds no host permissions, optional host permissions, content
scripts, tab URL persistence, analytics, or network upload path.

It connects only to `dev.gihwan.inkbeam.capture`. Inkbeam writes exactly one
Native Messaging host manifest and allows exactly the fixed extension origin.
No `com.myshottr.capture` alias is installed.

### 4.4 Capture scope

The v0.2.0 browser contract remains Chrome visible-viewport capture:

- capture the current web content viewport;
- exclude tabs, address bar, toolbar, side panels, and browser window chrome;
- do not stitch scrolled content;
- do not add a full-page fallback;
- transfer pixels through the local Native Messaging boundary only.

The architecture must keep viewport capture isolated from later full-page and
mockup composition features so those can be added without replacing the editor
document or capture request boundary.

## 5. Repository and Historical Release Transition

### 5.1 Repository rename

The public repository is renamed from `gihwan-dev/MyShottr` to
`gihwan-dev/inkbeam` without rewriting commits, issues, tags, releases, or
Actions history. After GitHub completes the rename:

1. update the local `origin` URL;
2. push the Inkbeam implementation branch to the renamed repository;
3. validate GitHub's redirect from the old repository URL;
4. update current README, badges, package links, install links, and appcast URLs;
5. merge only after CI runs against the exact renamed-repository commit.

The local parent checkout directory may remain named `MyShottr` while active
worktrees depend on it. A local directory rename is not part of v0.2.0.

### 5.2 Historical v0.1.0

The `v0.1.0` tag, release assets, checksums, release notes, and acceptance
evidence remain unchanged. The GitHub release is marked:

```text
Deprecated — pre-Inkbeam prototype
```

It is removed from current README download paths and is not present in either
Sparkle feed. Its exact GitHub state is `draft = false`,
`prerelease = true`, and `make_latest = false`. Its title begins with
`Deprecated —`, and its body starts with a banner stating that it is an
unsigned, pre-Inkbeam prototype. It remains available as historical evidence
and is not rewritten as an Inkbeam release.

## 6. Version, Channel, and Artifact Model

### 6.1 Version map

All Inkbeam release candidates use `CFBundleShortVersionString = 0.2.0`.
Sparkle compares the monotonically increasing numerical `CFBundleVersion`.

| Stage | Git tag | Short version | Build | GitHub state | Appcast |
| --- | --- | --- | --- | --- | --- |
| Historical | `v0.1.0` | `0.1.0` | `1` | Published deprecated pre-release | none |
| RC 1 | `v0.2.0-rc.1` | `0.2.0` | `2` | Pre-release | Beta |
| RC 2 | `v0.2.0-rc.2` | `0.2.0` | `3` | Pre-release | Beta |
| Final | `v0.2.0` | `0.2.0` | `4` | Latest release | Stable and Beta |

The RC label appears in the Git tag, release title, artifact name, appcast item
title, and read-only About diagnostic. It is not encoded in
`CFBundleShortVersionString`.

The Chrome extension uses manifest `version = 0.2.0`. RC naming may use
`version_name`; the extension remains manually reloaded from each release ZIP.

### 6.2 Public artifacts

`v0.2.0-rc.1` publishes:

- `Inkbeam-0.2.0-rc.1.dmg`
- `Inkbeam-Chrome-0.2.0-rc.1.zip`
- `SHA256SUMS.txt`

`v0.2.0-rc.2` publishes:

- `Inkbeam-0.2.0-rc.2.dmg`
- `Inkbeam-Chrome-0.2.0-rc.2.zip`
- `SHA256SUMS.txt`

`v0.2.0` publishes:

- `Inkbeam-0.2.0.dmg`
- `Inkbeam-Chrome-0.2.0.zip`
- `SHA256SUMS.txt`

The DMG contains exactly:

- `Inkbeam.app`;
- a symlink to `/Applications`.

No `.app.zip`, dSYM, private notary log, signing key, credential export, or
debug build is a public asset. Sparkle uses the same final stapled DMG published
on GitHub. Delta updates are disabled for v0.2.0.

## 7. Trust and Credential Boundary

### 7.1 Local release authority

The local release Mac is the sole signing and publication authority.

| Credential | Purpose | Storage |
| --- | --- | --- |
| Developer ID Application private key | app, helper, framework, and DMG signing | macOS login Keychain |
| Notarization credential | `notarytool` submission | `inkbeam-notary` Keychain profile |
| Sparkle EdDSA private key | update archive, feed, and release-note signing | macOS login Keychain |
| GitHub publishing credential | tags, releases, assets, and feed publication | local `gh` authentication |

The Developer ID and Sparkle EdDSA keys are distinct. Neither private key is
committed, exported into the workspace, written to an environment file, printed
to logs, or uploaded to GitHub Secrets.

The Sparkle public key is committed as one base64 line in
`Config/SparklePublicEDKey.txt`. Build generation injects that exact value into
the app's `SUPublicEDKey`. Release preflight derives the public key corresponding
to the Keychain private key with Sparkle's key tool and byte-compares all three
values: the committed file, the archived app's Info.plist value, and the
Keychain-derived public key. Any mismatch stops the release.

The release tools require an exact Team ID, signing identity, notary profile,
and Sparkle public/private key pair. They do not select an arbitrary identity.
If any required trust input is absent or inconsistent, the release stops before
publication. There is no unsigned official-release mode.

### 7.2 GitHub Actions boundary

GitHub Actions may:

- install locked source dependencies;
- run editor, extension, Swift, and static release-metadata tests;
- validate version, manifest, appcast XML shape, and public URLs;
- build non-published test products.

GitHub Actions may not:

- hold Developer ID, notarization, or Sparkle private credentials;
- sign or notarize the official app;
- create the official DMG;
- sign an appcast;
- publish a GitHub Release;
- change the stable feed.

Passing CI is necessary but does not prove a signed, notarized, installed, or
updated release.

## 8. Build, Signing, Notarization, and Packaging

### 8.1 Sparkle dependency

Swift Package Manager pins the exact Sparkle `2.9.4` release. The package does
not float to newer minor or patch versions. A Sparkle upgrade requires an
explicit dependency change and a repeated real updater acceptance sequence.

Inkbeam integrates new code through `SPUStandardUpdaterController`; it does not
use the deprecated `SUUpdater` API or implement a custom installer.

### 8.2 Signing order

The official archive uses Developer ID distribution with Hardened Runtime and
a secure timestamp. Nested code is signed from the inside out:

1. Sparkle Updater, XPC services, and helper executables;
2. `Sparkle.framework` and other nested frameworks;
3. `InkbeamNativeHost`;
4. `Inkbeam.app` as the outer app bundle;
5. the completed DMG as the outer distribution container.

Every executable is signed. The release contains no true
`com.apple.security.get-task-allow` entitlement.

### 8.3 Notarization and stapling

After signing:

1. create the read-only compressed DMG from the signed app;
2. sign the DMG with Developer ID Application;
3. submit that exact DMG through `notarytool` using the `inkbeam-notary`
   Keychain profile;
4. wait for the existing submission to reach a terminal result;
5. require `Accepted` and inspect the notary log;
6. staple the ticket to the DMG;
7. validate the staple;
8. run strict app and nested-code signature checks;
9. run Gatekeeper assessment against the final artifact;
10. calculate signatures and checksums only after stapling.

A long-running notarization retains and polls its submission ID. The release
tool does not create duplicate submissions automatically.

### 8.4 Final artifact seal

The final stapled DMG bytes are immutable. They are used to generate:

- Sparkle EdDSA enclosure signature;
- exact byte length for the appcast;
- SHA-256 for `SHA256SUMS.txt`;
- release-evidence metadata.

After publication, a tag/version/build asset is never silently replaced.

## 9. Sparkle Architecture and User Experience

### 9.1 Component boundary

`InkbeamApp` owns the menu command and user-visible app lifecycle.
`UpdateService` is a small wrapper around `SPUStandardUpdaterController` that
exposes manual checking and status without containing release credentials.
Sparkle owns feed loading, verification, download, replacement, and relaunch.
Developer-only release tools own signing and publication and are not embedded
in the app.

### 9.2 Channel configuration

RC and final builds derive their channel at build time:

- RC builds contain `appcast-beta.xml` as `SUFeedURL`;
- final builds contain `appcast.xml` as `SUFeedURL`.

There is no user-editable feed URL, beta toggle, hidden channel preference, or
runtime URL override. RC builds show `Release Candidate` and final builds show
`Stable` in read-only diagnostics.

The beta feed contains RC items and the final item so RC users can update to
the final build. The stable feed contains final releases only. Both feeds use
the same embedded Sparkle EdDSA public key.

### 9.3 Consent and update policy

- First launch performs no automatic update request and shows no updater
  permission prompt.
- A user-initiated `Check for Updates...` on first launch is allowed to make the
  requested network call.
- Second launch asks once whether automatic checks are allowed.
- If approved, checks run every 24 hours.
- If declined, scheduled checks remain disabled and the manual command remains
  available.
- Updates show version and release notes and require explicit installation.
- Automatic background download and silent installation are disabled.
- Sparkle system profiling is disabled.
- JavaScript in release notes is disabled.
- No analytics, telemetry, crash reporting, or user identity is added.

### 9.4 Required Sparkle security configuration

The release app contains:

- `SUPublicEDKey`;
- no `SUEnableAutomaticChecks` key, preserving Sparkle's second-launch consent
  prompt;
- `SUScheduledCheckInterval = 86400`;
- `SUAutomaticallyUpdate = NO`;
- `SUEnableSystemProfiling = NO`;
- `SUVerifyUpdateBeforeExtraction = YES`;
- `SURequireSignedFeed = YES`;
- `SUSignedFeedFailureExpirationInterval = 0`;
- HTTPS stable or beta `SUFeedURL`;
- explicit settings that prevent automatic download, automatic install, and
  system profiling.

Feed-signature failure never expires into an unverified presentation path.
Invalid appcast, release-note, archive, Developer ID, version, or URL validation
stops the update. Inkbeam does not try another asset, URL, or lower build.

### 9.5 Signed feeds and release notes

Sparkle's `generate_appcast` produces the appcast and required signatures using
the local Keychain EdDSA key. The v0.2.0 feed uses full DMG items only. Release
notes are embedded in the signed appcast for v0.2.0. The feed does not reference
an external `releaseNotesLink`; changing the embedded notes invalidates the feed
signature and blocks the feed.

## 10. Update Data Safety and Failure Handling

### 10.1 Modified documents

Accepting an update never bypasses Inkbeam's modified-document termination
decision. Before relaunch:

1. active capture/import work reaches a stable boundary;
2. each modified document receives the standard save, discard, or cancel
   decision;
3. save must complete successfully before termination;
4. discard proceeds only after the user's explicit choice;
5. cancel aborts both termination and installation.

Inkbeam does not reintroduce unsaved-document recovery snapshots or a recovery
chooser. The updater does not write or migrate `.inkbeam` documents.

### 10.2 Running from an unsuitable location

When launched from a read-only DMG or an App Translocation context, Inkbeam does
not initialize the updater, register the Chrome Native Messaging manifest, or
register global capture shortcuts. It shows an install-location explanation
and directs the user to move the app to a writable Applications location.

### 10.3 User-side failure invariants

Network failure, cancellation, insufficient space, permission failure, invalid
feed, invalid archive signature, invalid Developer ID, or relaunch failure must
not corrupt the installed app or an open document.

Signature failures:

- stop before extraction or installation;
- do not try another URL or asset;
- do not allow verification bypass;
- do not downgrade;
- present a concise user message and record a non-sensitive local diagnostic.

### 10.4 Chrome integration after an update

On each normal Inkbeam launch, the app validates the one current Native
Messaging manifest. It atomically replaces the manifest only when its helper
path, extension origin, or current contract differs. This is current-install
validation, not legacy migration.

The app, embedded helper, and Chrome extension maintain one versioned protocol
throughout the RC sequence. Sparkle updates only the macOS app. The extension
ZIP remains a separate manual installation artifact.

## 11. Privacy and Diagnostics

### 11.1 Network boundary

The updater may contact only:

- the configured Inkbeam GitHub Pages appcast;
- the signed Inkbeam GitHub Release DMG.

For v0.2.0, release notes are embedded in the signed appcast and create no
separate network request.

The app does not transmit:

- screenshot pixels;
- annotation or clipboard text;
- `.inkbeam` packages or file paths;
- Chrome tab URLs or browsing history;
- editor history;
- user or device identifiers;
- optional Sparkle system profile fields;
- analytics, telemetry, or crash reports.

Native and Chrome capture data remains local:

```text
Chrome extension
  -> local Native Messaging helper
  -> local Inkbeam inbox
  -> Inkbeam editor
```

No capture-data path connects to the update service.

### 11.2 Local update diagnostics

Local updater diagnostics may record:

- check start and finish time;
- current and discovered version/build;
- success, cancellation, or error category;
- Sparkle error code;
- configured appcast host;
- signature-validation outcome.

They must not record document names, capture contents, annotation text,
clipboard contents, Chrome URLs, Keychain values, or Apple/GitHub credentials.

## 12. Local Release Orchestrator

The release tool exposes bounded phases. Each phase verifies its inputs and
records non-secret evidence.

### 12.1 Preflight

- require a clean worktree;
- require the expected branch and exact commit SHA;
- require matching tag, short version, build, channel, and artifact names;
- require locked dependencies and Sparkle `2.9.4`;
- require exact Developer ID identity, Team ID, notary profile, and EdDSA key;
- require equality between the committed Sparkle public key, the archived
  `SUPublicEDKey`, and the public key derived from the Keychain private key;
- require all release-critical automated tests to pass;
- require old MyShottr processes to be stopped before environment cleanup.

The developer-only clean-cut preparation resolves and reports each old local
path. Before a clean installation test, the operator moves the old
`MyShottr.app` and `com.myshottr.capture.json` manifest to Trash after verifying
their exact paths. The release tool does not delete
`Application Support/MyShottr`, user projects, or any broad directory. Inkbeam
simply never reads them. Inkbeam does not ship cleanup behavior.

### 12.2 Archive, sign, package, and notarize

- generate the exact Xcode project;
- archive the correct RC or stable configuration;
- preserve dSYM privately;
- validate nested signing and entitlements;
- create, sign, notarize, staple, and assess the DMG;
- generate EdDSA, length, and SHA-256 metadata from the final DMG.

### 12.3 Publish and verify release candidates

For RC 1 and RC 2:

1. create and push the exact tag only after the local artifact passes signing,
   notarization, stapling, and artifact verification;
2. create the GitHub Release with `draft = false`, `prerelease = true`, and
   `make_latest = false`;
3. upload DMG, Chrome ZIP, and checksum assets;
4. download the public artifact and verify checksum, signature, staple, and
   Gatekeeper result;
5. prepare and validate the signed beta appcast locally;
6. publish the beta feed only after the artifact URL is live;
7. perform the release stage's required real installation or update;
8. complete the RC acceptance record.

An active RC title is `Inkbeam <tag>`. A withdrawn RC remains published with
the exact state `draft = false`, `prerelease = true`, and
`make_latest = false`, changes its title prefix to `Withdrawn —`, adds a body
banner explaining the reason, and is absent from the signed beta feed.

### 12.4 Verify and promote the final release

The final build must prove `RC 2 -> final` before it becomes stable:

1. create and push tag `v0.2.0` only after the final local artifact passes all
   local checks;
2. publish the final assets temporarily as a GitHub Pre-release with
   `draft = false`, `prerelease = true`, `make_latest = false`, and title
   `Inkbeam v0.2.0 (Final Candidate)`;
3. download and verify the public final DMG;
4. publish a signed beta feed containing final build 4;
5. update an installed RC 2 build 3 to final build 4 and complete all final
   beta-channel acceptance checks;
6. prepare and locally validate the signed stable appcast;
7. promote the same GitHub Release to `draft = false`, `prerelease = false`,
   `make_latest = true`, and title `Inkbeam v0.2.0`;
8. publish the already validated stable appcast;
9. verify the public stable feed and final release metadata;
10. publish README changes and release announcements.

If stable-feed publication or verification fails after step 7, the operator
must immediately return the GitHub Release to `prerelease = true` and
`make_latest = false`, restore the title `Inkbeam v0.2.0 (Final Candidate)`,
leave the previous stable feed unchanged, and make no stable announcement.
Promotion resumes only after a newly validated signed stable feed is ready.

A feed never points to an unavailable, draft-only, checksum-mismatched, or
unverified artifact. The beta feed may point to a verified public Pre-release
for staged acceptance. The stable feed may point only to a verified public
non-prerelease release.

### 12.5 Release evidence

The local process records:

- exact commit SHA, tag, version, build, and channel;
- public bundle identifiers and signing certificate identity;
- notary submission ID and result;
- artifact SHA-256 and byte length;
- public asset and appcast URLs;
- Gatekeeper and stapler verification results;
- automated and manual acceptance outcomes.

Each release stores its current non-secret phase state in an ignored local file
such as `build/release-evidence/<tag>/release-state.json`. A phase is marked
complete only after its verification succeeds. The state file supports audit
and deliberate continuation; it does not convert an incomplete phase into a
success.

Private dSYM, full notary log, and detailed build log remain outside public
release assets.

## 13. Release Failure and Withdrawal Policy

### 13.1 Before feed publication

Build, test, signing, notarization, stapling, checksum, public-download, or feed
signature failure blocks feed publication and announcement. An incomplete
candidate remains a Pre-release with `prerelease = true` and
`make_latest = false`; it is not described as stable.

### 13.2 Withdrawn release candidate

A bad RC is removed from the newly signed beta feed and receives the exact
withdrawn state defined in section 12.3. Its tag and asset are not silently
replaced. The correction uses the next build number and release-candidate tag.

### 13.3 Bad stable release

Inkbeam never performs an automatic downgrade. If a stable release has already
reached the signed feed:

1. remove the affected item from a newly signed feed to stop new installs;
2. document its impact on the GitHub Release;
3. publish the fix as `v0.2.1` with a higher build;
4. deliver the higher build through the normal signed update path.

If the affected app cannot launch, a separate official-GitHub manual recovery
instruction may direct users to the fixed DMG. The original `v0.2.0` asset is
never changed in place.

## 14. Automated Verification

### 14.1 Clean-cut scan

The source, configuration, generated project, built app, helper, Chrome ZIP,
DMG, appcast, and current user documentation fail verification if they contain
live MyShottr contracts, including:

```text
MyShottr
.myshottr
com.myshottr
MyShottrNativeHost
myshottr-editor
```

Historical release documents, the clearly superseded design, and this
authoritative design's explicit descriptions of removed identifiers are
file-level exceptions. Current README deprecation copy may be allowlisted by
exact line or structured section. No broad source or documentation directory
exception is allowed.

The scan also asserts:

- `.inkbeam` is the only registered editable project extension;
- `.myshottr` is rejected as unsupported;
- one Inkbeam Native Messaging manifest is generated;
- its `allowed_origins` contains exactly the fixed extension origin;
- no MyShottr Application Support or inbox path is read.

### 14.2 Product regression suites

Automated tests cover:

- `.inkbeam` create, save, reopen, edit, and resave;
- original pixels and annotation JSON round trips;
- rectangle, arrow, freehand, text, move, resize, and style operations;
- modified-document save, discard, and cancel decisions;
- clipboard copy and PNG export;
- native region-selection state and cancellation;
- Chrome visible-viewport capture logic;
- Native Messaging framing, request ownership, error reporting, and inbox handoff;
- fixed extension identity and exact permission surface;
- stable/beta feed selection and version comparison;
- first- and second-launch updater orchestration through injected updater state;
- signed-feed and archive configuration;
- a signed appcast with one mutated byte failing before update metadata is
  presented or a download starts;
- embedded release-note mutation failing signed-feed validation;
- a valid signed feed whose enclosure has an invalid Sparkle EdDSA signature
  failing before extraction;
- an EdDSA-valid test archive whose inner app has an invalid Developer ID
  signature failing before replacement;
- a non-incrementing build being ignored;
- an HTTP feed or asset URL being rejected.

Tests verify Inkbeam's integration and policies; they do not duplicate Sparkle's
internal implementation.

### 14.3 Artifact verification

Every candidate verifies:

- universal `arm64` and `x86_64` app and helper slices;
- strict nested code signatures from the expected Team ID;
- Hardened Runtime and secure timestamps;
- absence of debug entitlements;
- accepted notarization and a valid stapled ticket;
- Gatekeeper acceptance;
- exact DMG contents;
- final public SHA-256, byte length, and Sparkle signature;
- absence of secret keys, credential exports, dSYM, and junk files.

## 15. Manual Acceptance Environments

The minimum supported system remains macOS 15.0. Required environments are:

| Environment | Required phase | Required evidence |
| --- | --- | --- |
| Apple Silicon, release Mac on macOS 26.5.2 | RC 1, RC 2, final | full app, Chrome, updater, DMG, and privacy flow |
| Clean macOS 15.x user or VM | RC 1 and final | minimum-OS launch, Gatekeeper, save/open, and basic capture |
| Rosetta x86_64 on Apple Silicon | RC 1 and final | x86_64 app/helper launch and basic capture |
| Fresh stable Chrome profile | RC 1, RC 2, final | unpacked extension identity, host registration, and viewport capture |
| Reset Screen Recording permission | RC 1 and final | deny, explain, grant, and retry behavior |

The v0.2.0 release does not claim a physical Intel Mac test unless one is
actually run. Universal static verification, x86_64 automated tests, and a
Rosetta smoke test remain required.

Manual observation is mandatory for:

- first-download Gatekeeper behavior under quarantine;
- drag-to-Applications DMG UX;
- first-launch updater silence;
- the one-time second-launch consent prompt;
- Screen Recording permission UX;
- live region-selection feedback;
- toolbar-free Chrome viewport capture;
- macOS save/discard/cancel behavior during update relaunch;
- real `rc.1 -> rc.2 -> final` installed-app replacement;
- post-update document, native capture, and Chrome capture behavior.

These outcomes cannot be replaced by green unit tests or shell-only artifact
checks.

### 15.1 Updater consent and network evidence

First/second-launch acceptance uses two isolated fresh defaults profiles, one
for approval and one for decline. The exact candidate app runs while a
process-level network capture records requests to its configured appcast host.
An updater integration harness with a request-counting HTTPS endpoint supplies
repeatable automated evidence from the same source and settings.

Required observable results are:

- launch 1: zero automatic appcast requests before normal quit;
- launch 2 before a response: one consent prompt and zero appcast requests;
- approve branch: one request may occur only after approval;
- decline branch: zero appcast requests after decline;
- launch 3 in either branch: no repeat consent prompt;
- launch 3 after approval and a recent check: no extra request before the
  24-hour interval;
- injected-clock automation: exactly one scheduled request becomes eligible
  after 86,400 seconds.

The acceptance record attaches the sanitized request-count or process-network
log. Visual observation of “no prompt” alone does not prove network silence.

## 17. Release Blockers

Any of the following blocks a final release:

- no valid Developer ID identity;
- notarization not accepted;
- invalid app, helper, DMG, appcast, or release-note signature;
- Gatekeeper requiring a bypass procedure;
- an automatic first-launch updater network request;
- loss of modified content without an explicit discard decision;
- live `.myshottr`, `com.myshottr.*`, or MyShottr runtime contracts;
- failed native region capture;
- failed Chrome visible-viewport capture;
- browser chrome included in the captured image;
- unverified `rc.1 -> rc.2` or `rc.2 -> final` update;
- public checksum mismatch;
- a feed item pointing to an unavailable or unverified asset;
- a skipped, flaky, or failing release-critical test.

Documented non-core copy or cosmetic issues may remain. Installation, trust,
update, data safety, privacy, and core capture defects may not.

features, and visual redesign are excluded.

## 21. Completion Definition

This design is implemented only when:

1. the repository and all live product surfaces use Inkbeam only;
2. the old compatibility and migration paths do not exist;
3. RC 1, RC 2, and final artifacts satisfy their respective release gates;
4. the final signed stable and beta feeds are live;
5. public artifacts match local signed evidence;
6. the README names the actual supported scope and installation requirements;
7. the exact final commit, release, and runtime results are recorded;
8. there is no remaining release blocker.

Until all eight conditions hold, the work may be described as design,
implementation, signed candidate, notarized candidate, or release candidate as
appropriate, but not as a completed official Inkbeam v0.2.0 release.
